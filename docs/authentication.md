# Авторизация

Бэкенд выдаёт access JWT на 15 минут. Refresh JWT действует до 28 дней с момента входа, передаётся только в cookie `am_refresh` (`HttpOnly`, `SameSite=Strict`, `Secure` вне dev/test, путь `/api/user/user`) и ротируется при каждом обновлении. Access хранится только в памяти фронтенда. В БД сохраняются SHA-256 хеши токенов, срок действия и идентификатор сессии.

Подпись, алгоритм, issuer, audience, тип и срок JWT проверяются до обращения к БД. Отозванные токены и неактивные пользователи не получают доступ. Роль читается из актуальной записи пользователя. При выходе отзываются все поколения токенов текущей сессии; другие устройства сохраняют вход. Повторное использование старого refresh отзывает всю его сессию. Ротация и отзыв сериализуются транзакционной блокировкой строки пользователя. Истёкшие записи токенов удаляются ежедневно.

## API

- `POST /api/user/user/register`: email и пароль, регистрация; 5 запросов в минуту с IP.
- `POST /api/user/user/sign-in`: email и пароль; JSON содержит только `access`, refresh устанавливается в cookie; 10 запросов в минуту с IP.
- `POST /api/user/user/refresh`: без тела и без действующего access, использует refresh cookie, возвращает новый access и обновляет cookie.
- `POST /api/user/user/logout`: без тела и без действующего access; отзывает сессию по cookie и удаляет cookie; ответ 204.
- `GET /api/user/user/profile`: Bearer access, профиль содержит только явно разрешённые поля.

Все POST выше требуют `X-CSRF-Protection: 1` и отклоняют `Sec-Fetch-Site: cross-site`. Фронтенд добавляет заголовок автоматически. Приложение работает с API на том же origin; CORS для сторонних origin не включён. Разрешение credentialed CORS требует отдельной проверки доверенных origin.

Ошибки входа для отсутствующего email, неверного пароля и неактивного пользователя одинаковы: 401 с `code: INVALID_CREDENTIALS`. Закрытые ручки отвечают 401 без авторизации и 403 при недостаточной роли. Ограничение запросов отвечает 429 с `code: TOO_MANY_REQUESTS` и `Retry-After`.

Фронтенд восстанавливает сессию до начальной маршрутизации, объединяет параллельные обновления и повторяет запрос после 401 один раз. Web Locks сериализует обновления между вкладками в поддерживающих браузерах. Явный выход отмечается несекретным флагом `am_logged_out`, чтобы не восстанавливать сессию при перезагрузке после сетевой ошибки logout.

## Обновление окружения

1. Установить зависимости через `npm ci`.
2. Задать случайный `JWT_SECRET` длиной не менее 32 символов для production. Изменение секрета завершает существующие сессии.
3. Применить миграцию `SecureAuthSessions1792700000000` командой `npm run am:back:typeorm:migration:run` до запуска нового бэкенда. Миграция отзывает старые токены и удаляет их исходные значения. Пользователям потребуется повторный вход. Откат схемы не восстанавливает старые сессии.
4. Обновить бэкенд и фронтенд совместно: контракт refresh/logout и формат ответа входа изменились. Production требует HTTPS для Secure cookie.
5. При наличии reverse proxy задать `TRUST_PROXY` как список его доверенных IP/подсетей через запятую, например `loopback` для локального прокси. Это позволяет ограничивать попытки по IP клиента. Не доверять заголовкам произвольных клиентов.

Ограничитель запросов хранит счётчики в памяти процесса. При нескольких экземплярах бэкенда нужен общий storage ограничителя или ограничение на общем прокси. Пароли новых аккаунтов: от 8 символов, строчные и прописные латинские буквы и цифры, не более 72 байт UTF-8 (ограничение bcrypt).
