# Платёжные попытки (AMS-10)

Перед запуском применить `1794000000000-payment-attempts` стандартной командой
`npm run am:back:typeorm:migration:run`.

`PaymentService` и репозиторий попыток зарегистрированы в `OrderDomainModule`,
чтобы использовать общий порядок блокировок пользователя и заказа. Наружу
экспортируется только сервис. Сущности и репозитории остаются внутри домена.

## API и повторы

`POST /api/orders/:id/payments`, `@Auth()`, тело:

```json
{ "idempotencyKey": "c5d5817f-1f33-4e1a-9a25-126745a79f98" }
```

Принимается только UUID v4. Владелец берётся из авторизации, сумма и валюта —
из неизменяемого заказа, return URL — из серверного `SITE_URL`.
Клиентские суммы, userId, provider, status и URL отклоняются. Ответ HTTP 201
содержит безопасный `PaymentAttemptDto`; внешние ID, внутренние ошибки и UUID
провайдера не выдаются.

1. Транзакция блокирует пользователя, затем активный заказ. Оплата допустима
   только для собственного оформленного `PENDING_PAYMENT`, без административного
   источника, до `paymentExpiresAt`, с положительной безопасной целочисленной
   суммой в RUB/USD. При равенстве срока времени БД платить уже нельзя.
2. UUID повторного запроса привязывается к исходной попытке. Если разные вкладки
   прислали разные UUID к активной попытке, оба ключа сохраняют ссылку на неё,
   в том числе после её отказа/отмены. `payment_request` хранит эти соответствия.
   Для нового списания после FAILED/CANCELLED требуется новый UUID.
3. Резерв `PENDING` и ключ внешней идемпотентности коммитятся **до** вызова
   провайдера. Внешний запрос выполняется без DB-lock, ожидание ограничено 10 с.
   Повтор всегда использует тот же ключ и денежный snapshot. Реальный адаптер
   обязан обеспечить идемпотентность у провайдера, включая потерю ответа.
4. Следующая транзакция блокирует пользователя → заказ → попытку, сверяет
   externalId, orderId, сумму, валюту и нормализованный статус. Авторизация
   остаётся `PENDING`; только финальное списание с `captured=true` и `paidAt`
   даёт `SUCCEEDED`. Терминальный результат не перезаписывается поздним ответом.
   Финансовый результат сохраняется даже при конкурентной отмене заказа,
   но ссылка для оплаты отменённого/просроченного заказа не возвращается.

`PAYMENT_UNAVAILABLE` / 503 оставляет попытку незавершённой: повторить с прежним
UUID, а не создавать замену. Подробности и секреты ошибки провайдера наружу
не передаются. `PAYMENT_CONFLICT` / 409 означает UUID другого заказа/провайдера
или уже списанный платёж. Чужой/отсутствующий/неактивный заказ — `NOT_EXIST` / 400;
недопустимые статус, срок и деньги — `INVALID` / 400. `SUCCEEDED` блокирует новые
попытки, даже пока заказ ожидает финализации.

## Модель и legacy

Заказ имеет `OneToMany payments`; попытка хранит `ManyToOne order`, провайдера,
externalId, уникальный idempotencyKey, состояние, amount/currency, confirmationUrl,
paidAt, checkedAt и безопасный errorCode. Суммы — bigint в минимальных единицах,
ограниченные диапазоном безопасных JS integers. Индексы обеспечивают одну PENDING
попытку на заказ и уникальную пару provider/externalId при ненулевом externalId.
Триггер защищает денежный snapshot, ключ, связь, внешний ID и терминальный статус.

Миграция переносит прежний `order.paymentId` в `payment.order_id`, сохраняет
`totalPrice` и записи без заказов. У legacy provider=`legacy`, status, amount и
currency остаются NULL: валюта и факт списания исторически неизвестны.
Существующие PAID и административные заказы не меняются.
Откат восстанавливает старую связь только до появления новых попыток;
при наличии финансовой истории он останавливается без удаления данных.

## Mock и границы следующего этапа

Токен `PAYMENT_PROVIDER` сейчас указывает на `MockPaymentProvider`. Он разрешён
только в `NODE_ENV=dev/test`; production и неизвестное окружение дают 503 до
создания попытки. В dev используется `SITE_URL` либо `http://localhost:4400`;
mock возвращает ссылку на детали заказа, ничего не списывает и по умолчанию
оставляет попытку PENDING. Его состояние в памяти предназначено для тестирования,
а не для финансового production-хранилища; ID детерминирован по UUID.

`enqueueScenario` доступен **только** в test: успех, отказ, авторизация, отмена,
задержка и потеря ответа после создания. Публичных endpoint управления mock нет.
Контракт содержит create/get/cancel/refund; refund явно не реализован.

Фронтенд блокирует двойной запрос, сохраняет UUID при ошибке, отменяет устаревшие
подписки при смене заказа/авторизации и переходит только по безопасной ссылке.
Ни redirect, ни query-параметры не переводят заказ в PAID.

Webhook, return-page с проверкой статуса, периодическая сверка, централизованная
финализация заказа, выдача прав и компенсация позднего списания — AMS-12/AMS-11.
Для них подготовлены внешний ID, providerStatus, checkedAt и `getPayment` /
`cancelPayment` в контракте. Обработчиков уведомлений, реального агрегатора,
фискализации, скидок и бизнес-логики возвратов здесь нет.

## Проверки

```sh
npx nx run am-back:test --runInBand --testPathPatterns=payment
PAYMENT_TEST_DATABASE_URL=postgres://user:password@localhost:5432/postgres \
  npx nx run am-back:test --runInBand --testPathPatterns=payment.postgres
```

Интеграционные тесты создают случайную отдельную БД `ams10_test_*` и удаляют её
после выполнения; исходная БД не изменяется. Требуется право CREATE DATABASE.
Покрыты up/down с legacy-связями и orphan-записями, конкуренция запросов/UUID,
ошибки провайдера/записи результата/резерва, запрет повторного списания, ограничения
БД, отмена во время внешнего запроса и сохранение финансового аудита.
