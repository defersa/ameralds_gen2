# Платёжные попытки и подтверждение покупки (AMS-10, AMS-12)

Перед запуском применить `1794000000000-payment-attempts` стандартной командой
`npm run am:back:typeorm:migration:run`, а также новую миграцию
`1794500000000-payment-completion`. Основная БД при разработке автоматически не мигрируется.

`PaymentService` и репозиторий попыток зарегистрированы в `OrderDomainModule`,
чтобы использовать общий порядок блокировок пользователя и заказа. Наружу
экспортируются сервисы создания и проверки оплаты. Сущности и репозитории остаются внутри домена.

## API и повторы

`POST /api/orders/:id/payments`, `@Auth()`, тело:

```json
{ "idempotencyKey": "c5d5817f-1f33-4e1a-9a25-126745a79f98" }
```

Принимается только UUID v4. Владелец берётся из авторизации, сумма и валюта —
из неизменяемого заказа, return URL — из серверного `SITE_URL`.
Клиентские суммы, userId, provider, status и URL отклоняются. Ответ HTTP 201
содержит безопасный `PaymentAttemptDto`; внешние ID, внутренние ошибки и UUID
провайдера не выдаются.

1. Транзакция блокирует пользователя, затем активный заказ. Оплата допустима
   только для собственного оформленного `PENDING_PAYMENT`, без административного
   источника, до `paymentExpiresAt`, с положительной безопасной целочисленной
   суммой в RUB/USD. При равенстве срока времени БД платить уже нельзя.
2. UUID повторного запроса привязывается к исходной попытке. Если разные вкладки
   прислали разные UUID к активной попытке, оба ключа сохраняют ссылку на неё,
   в том числе после её отказа/отмены. `payment_request` хранит эти соответствия.
   Для нового списания после FAILED/CANCELLED требуется новый UUID.
3. Резерв `PENDING` и ключ внешней идемпотентности коммитятся **до** вызова
   провайдера. Внешний запрос выполняется без DB-lock, ожидание ограничено 10 с.
   Повтор всегда использует тот же ключ и денежный snapshot. Реальный адаптер
   обязан обеспечить идемпотентность у провайдера, включая потерю ответа.
4. Следующая транзакция блокирует пользователя → заказ → попытку, сверяет
   externalId, orderId, сумму, валюту и нормализованный статус. Авторизация
   остаётся `PENDING`; только финальное списание с `captured=true` и `paidAt`
   даёт `SUCCEEDED`. Устаревший отказ не перезаписывает списание. Подтверждённое позднее списание
   может заменить FAILED/CANCELLED, но отменённый заказ при этом не становится PAID.
   Финансовый результат сохраняется даже при конкурентной отмене заказа,
   но ссылка для оплаты отменённого/просроченного заказа не возвращается.

`PAYMENT_UNAVAILABLE` / 503 оставляет попытку незавершённой: повторить с прежним
UUID, а не создавать замену. Подробности и секреты ошибки провайдера наружу
не передаются. `PAYMENT_CONFLICT` / 409 означает UUID другого заказа/провайдера
или уже списанный платёж. Чужой/отсутствующий/неактивный заказ — `NOT_EXIST` / 400;
недопустимые статус, срок и деньги — `INVALID` / 400. `SUCCEEDED` блокирует новые
попытки, даже пока заказ ожидает финализации.

## Модель и legacy

Заказ имеет `OneToMany payments`; попытка хранит `ManyToOne order`, провайдера,
externalId, уникальный idempotencyKey, состояние, amount/currency, confirmationUrl,
paidAt, checkedAt и безопасный errorCode. Суммы — bigint в минимальных единицах,
ограниченные диапазоном безопасных JS integers. Индексы обеспечивают одну PENDING
попытку на заказ и уникальную пару provider/externalId при ненулевом externalId.
Триггер защищает денежный snapshot, ключ, связь, внешний ID и терминальный статус.

Миграция переносит прежний `order.paymentId` в `payment.order_id`, сохраняет
`totalPrice` и записи без заказов. У legacy provider=`legacy`, status, amount и
currency остаются NULL: валюта и факт списания исторически неизвестны.
Существующие PAID и административные заказы не меняются.
Откат восстанавливает старую связь только до появления новых попыток;
при наличии финансовой истории он останавливается без удаления данных.

## Подтверждение и завершение покупки

`GET /api/orders/:id/payment-state` требует авторизацию и проверяет владельца до вызова провайдера.
Ответ не кешируется. Сервер возвращает статус заказа, попытки, время проверки, признак
недоступности проверки и `resolution`: `completed`, `compensation_required` либо NULL.
Частота HTTP ограничена 30 запросами в минуту; общая аренда в БД ограничивает обращения
к API одной попытки между вкладками и экземплярами сервера. Redirect и query params
не меняют состояние оплаты.

Все результаты проходят `PaymentService.processPaymentResult`: блокировка пользователя →
заказа → попытки, проверка provider/externalId/orderId/суммы/валюты и окончательного списания.
В одной транзакции фиксируются SUCCEEDED и PAID/paidAt, выдаются права через
`PatternGrantsService`, отменяются **все** остальные PENDING_PAYMENT пользователя с причиной
`another_order_paid`, полностью очищается текущая OPEN-корзина и записывается outbox.
Ошибки выдачи прав или очистки откатывают всю операцию. Дубликат не очищает новую корзину.

Списание по отменённому, неактивному или уже оплаченному другой попыткой заказу,
после срока оплаты либо с пересечением уже действующих прав получает
`resolution=compensation_required`. Финансовый результат и outbox-инцидент сохраняются,
права не выдаются, заказ не переводится автоматически в PAID. Автоматического возврата нет.
Состояние требует ручного финансового разрешения в следующем этапе; событие
`payment_compensation_required` передаётся в журнал мониторинга. Подтверждение доставки
этого события не разрешает сам финансовый инцидент.

`PaymentEffectsService` после коммита отправляет письмо и отменяет активные попытки
других заказов. Резерв без externalId восстанавливается по исходному ключу перед отменой.
Очередь имеет уникальные ключи, аренду с SKIP LOCKED и счётчиком попыток, повторы с backoff
до часа. Семантика at-least-once: при сбое после SMTP возможен повтор письма
с тем же Message-ID. Отсутствие SMTP оставляет письмо в очереди для повтора.

Раз в минуту сервер сверяет ограниченную порцию, независимо от наличия webhook.
Незавершённые попытки проверяются без ограничения возраста; FAILED/CANCELLED — в окне
поздних списаний от времени создания. Ошибки API увеличивают паузу до часа.
Зависшие попытки отмечаются событием `payment_stuck`. Настройки:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `PAYMENT_RECONCILE_BATCH` | 50 | Размер порции, максимум 500 |
| `PAYMENT_RECHECK_SECONDS` | 5 | Минимальная пауза проверки PENDING через API/cron |
| `PAYMENT_TERMINAL_RECHECK_SECONDS` | 3600 | Пауза проверки FAILED/CANCELLED |
| `PAYMENT_TERMINAL_RECHECK_DAYS` | 7 | Окно сверки терминальных отказов/отмен |
| `PAYMENT_STUCK_AFTER_HOURS` | 24 | Порог предупреждения о зависшем PENDING |

Cron имеет минутную гранулярность, UI опрашивает статус каждые 5 секунд до двух минут
и позволяет проверить его вручную. После подтверждения корзина и права перечитываются;
другие вкладки получают сигнал через storage: видимые перечитывают данные сразу,
скрытые — при возврате пользователя. События focus и visibilitychange приводят к одному обновлению с минимальной
паузой 30 секунд между автоматическими запросами. Событие покупки обходит эту паузу;
в скрытой вкладке или во время запроса оно сохраняется до следующего обновления.
Постоянного фонового таймера на frontend нет. Поздняя оплата без открытой страницы результата
отображается при следующем возврате во вкладку. Данные storage не служат доказательством оплаты.

## Mock, webhook и границы интеграции

Токен `PAYMENT_PROVIDER` сейчас указывает на `MockPaymentProvider`. Он разрешён
только в `NODE_ENV=dev/test`; production и неизвестное окружение дают 503 до
создания попытки. В dev используется `SITE_URL` либо `http://localhost:4400`;
mock возвращает ссылку на детали заказа, ничего не списывает и по умолчанию
оставляет попытку PENDING. Его состояние в памяти предназначено для тестирования,
а не для финансового production-хранилища; ID детерминирован по UUID.

`enqueueScenario` доступен **только** в test: успех, отказ, авторизация, отмена,
задержка и потеря ответа после создания. Публичных endpoint управления mock нет.
Контракт содержит create/get/cancel/refund; refund явно не реализован.

Фронтенд блокирует двойной запрос, сохраняет UUID при ошибке, отменяет устаревшие
подписки при смене заказа/авторизации и переходит только по безопасной ссылке.
Ни redirect, ни query-параметры не переводят заказ в PAID.

`POST /api/payment-webhooks/:provider` принимает уведомление только после проверки
адаптером `verifyWebhook`; адаптер без этого метода запрещает webhook.
Mock требует `PAYMENT_MOCK_WEBHOOK_SECRET` и заголовок `x-payment-signature`:
hex HMAC-SHA256 строки externalId. Тело `{ "externalId": "mock_..." }`.
Любые финансовые поля тела игнорируются: результат перечитывается через getPayment.
Неизвестный внешний ID или ошибка записи дают 503 для повторной доставки;
недействительная подпись — 401, успешный коммит — 204.
Контроль `setResult` доступен исключительно тестам в NODE_ENV=test.

Реальный адаптер должен реализовать проверку подлинности по правилам провайдера,
нормализацию UNKNOWN/авторизации/окончательного списания и надёжное внешнее хранение.
Ни ключей реального агрегатора, ни фискализации, скидок и Refund API здесь нет.

## Проверки

```sh
npx nx run am-back:test --runInBand --testPathPatterns=payment
PAYMENT_TEST_DATABASE_URL=postgres://user:password@localhost:5432/postgres \
  npx nx run am-back:test --runInBand --testPathPatterns='payment.*postgres'
```

Интеграционные тесты создают случайные отдельные БД `ams10_test_*` / `ams12_test_*` и удаляют их
после выполнения; исходная БД не изменяется. Требуется право CREATE DATABASE.
Покрыты up/down с legacy-связями и orphan-записями, конкуренция запросов/UUID,
ошибки провайдера/записи результата/резерва, запрет повторного списания, ограничения
БД, отмена во время внешнего запроса и сохранение финансового аудита. AMS-12 дополнительно
проверяет три канала подтверждения, дубликаты, конкурирующие списания, позднее списание,
ошибку выдачи прав и откат, полную очистку корзины, потерю ответа после коммита,
проверку подписи, денежного snapshot, владельца, backoff и повтор outbox.
