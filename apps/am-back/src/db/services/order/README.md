# Пользовательский заказ, корзина и checkout (AMS-7 — AMS-9)

Одна `UserOrderEntity` хранит корзину и оформленный заказ. Перед запуском приложения
применить миграции (`npm run am:back:typeorm:migration:run`).

## Статусы и совместимость

| Имя в домене | Значение в БД и API |
| --- | --- |
| OPEN | open |
| PENDING_PAYMENT | pending_payment |
| PAID | success |
| CANCELLED | cancel |
| PARTIALLY_REFUNDED | partially_refunded |
| REFUNDED | refunded |

Значения `success` и `cancel` сохранены. Существующие права и административные
заказы не переоформляются. Новые статусы возвратов — подготовка модели;
платёжные попытки, провайдер и механика возвратов здесь не реализованы.

У одного пользователя может быть только одна ACTIVE-корзина OPEN. Ограничение
обеспечивает partial unique index; `ON CONFLICT DO NOTHING` позволяет конкурентно
создавать корзину. У заказов без пользователя такого ограничения нет. Количество
PENDING_PAYMENT не ограничено. Миграция объединяет состав дублирующих корзин в
последней активной, объединяет размеры и цвет повторяющихся схем и архивирует
освободившиеся корзины.

## Деньги и история

`subtotalAmount`, `discountAmount`, `totalAmount` — безопасные целые минимальные
единицы валюты (копейки RUB / центы USD), в БД `bigint`. Цены каталога decimal
переводятся в эти единицы без умножения floating point на 100. Слишком точные,
отрицательные и выходящие за безопасный диапазон цены отклоняются. Существующая
тарифная формула `getPatternPrice` сохранена.

Позиция содержит JSONB `snapshot`: идентификатор и название схемы ru/en,
выбранные размеры (ID варианта, ID и значение размера), цвет, флаг покупки,
валюту, суммы и компоненты base/size/color с количеством и ценой единицы.
На заказе и позиции предусмотрен `discounts` с `type`, `name`, `amount` и
опциональным `sourceId`. Пока `discountAmount=0`, `discounts=[]`,
`totalAmount=subtotalAmount`; применения скидок нет.

OPEN и legacy-записи могут иметь `subtotalAmount`, `totalAmount`, `currency`
и snapshot позиции равными NULL; скидка по умолчанию 0, список скидок пуст.
NULL означает неизвестную историческую цену, а не бесплатную покупку.
Миграция не восстанавливает её из изменяемого каталога. Старые pending без
денежного snapshot отменяются с причиной `legacy_missing_price_snapshot`.
`paidAt` для старых покупок остаётся NULL, так как достоверное время оплаты неизвестно.

Новые личные покупки из административных заказов получают snapshot в RUB
(существующий административный сценарий считает цену ru), `paidAt` и статус PAID
в той же транзакции с выдачей прав. При отсутствии удалённой схемы достоверная
цена остаётся NULL. Сборка такого заказа использует временный INACTIVE OPEN,
поэтому активная пользовательская корзина сохраняется.

`GET /orders/:id` проверяет владельца и возвращает оформленный заказ, включая
PENDING_PAYMENT. OPEN-корзины этим методом недоступны. Страница `/account/orders/:id`
загружает заказ независимо от checkout, показывает его карточками без редактирования
и предлагает оплату с временно заблокированной кнопкой «Оплатить».
Данные названия, размеров, цвета и стоимости берутся из snapshot; для старых
записей без snapshot остаётся прежнее представление. Приватные пути файлов,
пользователь и административный заказ в DTO не попадают.

## Нормализация корзины (AMS-8)

Все операции личной корзины, включая GET, блокируют сначала пользователя, затем
OPEN-заказ. Выдача прав использует ту же блокировку пользователя: проверка корзины
после ожидания видит зафиксированные права. Блокировка корзины и уникальный индекс
сохраняют инвариант одной OPEN-корзины. Для будущей выдачи и отзыва прав сохранять
этот порядок блокировок; checkout должен повторно проверять права в своей транзакции.

Из выбора исключаются действующие приобретённые размеры и цвет, повторяющиеся
размеры и недоступные варианты каталога. Цвет — одно дополнение на схему; без новых
размеров он допустим только владельцу хотя бы одного действующего размера.
Пустая после проверки позиция удаляется. Флаг `requiresPatternPurchase` вычисляется
сервером по действующим размерам, клиентский флаг не подтверждает владение.
Неактивные записи прав не препятствуют повторной покупке.

Merge объединяет повторяющиеся локальные записи одной схемы перед нормализацией.
Ответ `CartDto` сохраняет `cart` и `price` и содержит `correctedPatternIds`:
идентификаторы схем, выбор которых скорректирован или полностью удалён.
Фронтенд принимает этот состав и уведомляет о корректировке. Локальная копия
очищается после успешного merge. Административная корзина использует прежние правила.

## Checkout (AMS-9)

`POST /orders/checkout` доступен только авторизованному владельцу корзины.
Тело запроса: `{ cartId, cartRevision, currency: "RUB" | "USD" }`.
`cartId` и `cartRevision` берутся из ответа личной корзины (`cart.id`, `revision`).
Суммы, userId и неизвестные поля в запросе отклоняются.

`PlaceOrderService` выполняет оформление в одной транзакции: блокирует пользователя
перед заказом, проверяет владельца и состояние, сравнивает подтверждённый состав,
заново проверяет права и доступность схем, размеров и цвета. Если состав или права
изменились, возвращает HTTP 409 `{ code: "CART_CONFLICT", entity: "cart", items }`.
В `items` — ID позиции и схемы, название, размеры, цвет и причины конфликта.
Корзина при конфликте не изменяется. Пользователь отдельно обновляет её через GET
и повторно подтверждает исправленный состав.

Успешное оформление фиксирует цену каталога и snapshot через `OrderCheckoutService`:
`discountAmount=0`, `discounts=[]`, `totalAmount=subtotalAmount`.
`sumOrderSnapshots` остаётся точкой расширения расчёта; механизм скидок не добавлен.
Затем по текущим AppSettings и времени БД фиксируются `placedAt`, `paymentExpiresAt`
и `appSettingsVersion`, заказ переходит в PENDING_PAYMENT. Дата оформления хранится
в новой nullable колонке `placed_at` (миграция `1793900000000-checkout-placement`);
старые даты не восстанавливаются. Дата, срок, суммы, позиции и snapshot защищены
после оформления триггерами. Новая пустая OPEN-корзина создаётся в той же транзакции checkout.
Фронтенд обновляет её состав и стоимость перед переходом на страницу заказа.

Исходный `cartId` служит устойчивым ключом повторов: повтор с той же валютой
возвращает тот же оформленный заказ и его snapshot, даже после создания следующей
OPEN-корзины, изменения цен, настроек или дальнейшего закрытия заказа. Срок не
продлевается, права повторно не выдаются. Повтор с иной валютой отклоняется.
Клиент сохраняет попытку в sessionStorage текущей вкладки до успешного обновления
корзины после checkout либо явного обновления после конфликта; это позволяет восстановить ответ после перезагрузки или потери соединения.

Ответ содержит ID, статус, исторический состав и суммы, время оформления, срок
оплаты и версию настроек. Секреты пользователя и приватные пути файлов не выдаются.
Создание платёжных попыток и переход по ссылке описаны в
[AMS-10](../payment/README.md). Переход по ссылке не завершает заказ.

## Ручная отмена

`POST /api/orders/:id/cancel` отменяет собственный активный `PENDING_PAYMENT` и возвращает
`UserOrderSummaryDto` с актуальными статусом, датами и суммами. Владелец берётся из
авторизации; переданные в теле `userId` или статус не используются.

`CancelUserOrderService` в одной транзакции блокирует пользователя, затем заказ.
Отмена фиксирует время БД и причину `user_cancelled`, не меняя состав, стоимость,
срок оплаты или текущую корзину. Повтор для отменённого заказа сохраняет прежние
дату и причину, включая отмену по истечению срока оплаты. Чужой, отсутствующий
или неактивный заказ возвращает `NOT_EXIST`, остальные статусы и административный
источник — `INVALID`. Обе ошибки имеют HTTP 400.

На странице заказа действие доступно только в `PENDING_PAYMENT`. После успешного
ответа обновляются основные поля заказа, состав сохраняется; повторный запрос
блокируется во время загрузки. При смене заказа или авторизации устаревший ответ
не применяется к новой странице.

## Структура

```text
order/
  order.module.ts
  cart/          # UserCartService, AdminCartService и общий выбор позиции
  user/          # UserOrderService: история; CancelUserOrderService: отмена ожидающей оплаты
  admin/         # AdminOrderService, AdminOrderMailService и доступ к файлам
  checkout/      # OrderCheckoutService, OrderExpirationService и срок оплаты
  pricing/       # чистые расчёты сумм и снимков, без NestJS и TypeORM
  mappers/       # DTO корзин и заказов
  repositories/  # запросы и блокировки; приватные провайдеры
  errors/        # перевод доменных ошибок в ошибки API
  types/         # контракты внутренних операций
```

`OrderDomainModule` содержит сервисы по областям ответственности. Работа
с корзиной не смешивается с чтением истории или отправкой писем. Связанные операции
одного заказа находятся вместе: `AdminOrderService` читает, перечисляет и завершает
административные заказы, `UserOrderService` читает личный заказ и создаёт покупку
из административного. `OrderCheckoutService` фиксирует и цену, и срок оплаты.

Изменения корзины выполняются в одной транзакции с блокировкой строки заказа;
общая административная корзина дополнительно использует advisory lock. Список
административных заказов читается в REPEATABLE READ, письмо отправляется после
коммита. EntityManager передаётся каждому запросу, участвующему в транзакции.

Расчёт snapshot принимает `OrderSnapshotInput` — обычные данные выбора,
без сущностей или HTTP-ошибок. `InvalidOrderPriceError` преобразуется в привычную
ошибку API на границе сервиса. Мапперы отдельно определяют поля ответов.

Модуль экспортирует сервисы; репозитории и фоновая автоотмена остаются приватными.
`UserOrderService.createFromAdminOrder(adminOrderId, manager)` возвращает ID личного
заказа либо null для заказа без email. Общие сервисы каталога, пользователей и
файлов находятся в `DbInfrastructureModule`.

## Проверки PostgreSQL

```sh
ORDER_TEST_DATABASE_URL=postgres://postgres:password@127.0.0.1:5432/postgres \
  npx nx run am-back:test --runInBand --testPathPatterns='order.postgres|order-snapshot'
```

Требуется CREATE DATABASE. Тесты создают и удаляют собственную случайную БД
`ams7_test_*`; исходная БД из URL не изменяется. Проверяются настоящие миграции
AMS-5 → AMS-7, legacy-данные, конкурентные корзины, обходы ограничений,
удаление каталога, административные покупки, rollback и транзакционная отмена.
Без переменной пропускаются только PostgreSQL-тесты.
