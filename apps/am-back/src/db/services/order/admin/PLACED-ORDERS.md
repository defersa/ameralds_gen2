# Административный просмотр пользовательских заказов (AMS-14)

Страницы `/admin/orders` и `/admin/orders/:id` работают с `UserOrderEntity`.
Старые страницы `/admin/orders/list` и `/admin/orders/card/:id` относятся к административным корзинам и сохраняют свои маршруты.

API `/api/admin/orders` требует авторизацию и ADMIN. Список исключает OPEN, включает исторические и созданные из административных заказов записи. Фильтры: `statuses` через запятую, `user` (часть email без учёта регистра или точный ID), `from`/`to` (YYYY-MM-DD), `page`, `pageSize` (1–100). Даты отображаются в UTC, обе календарные границы включены. Для `createdAt` используются Date-параметры с той же сериализацией драйвера, что и при чтении timestamp; строковые границы без приведения не эквивалентны этому поведению. Сортировка: createdAt DESC, id DESC. Ответ содержит total, count страниц, page и pageSize.

Детали читаются в REPEATABLE READ, чтобы статус заказа, операция возврата и предупреждения о правах соответствовали одному снимку БД. Товарные и денежные snapshot не пересчитываются по каталогу. Внешние ID платежей доступны администратору; ключи идемпотентности, URL подтверждения и секреты в DTO не включаются.

POST `/:id/cancel` и `/:id/refund` принимают только `{ reason: string }`, максимум 2000 символов. Дополнительные поля, включая сумму и позиции, отклоняются. Инициатор берётся из RequestModel и повторно проверяется по БД.

Отмена использует блокировки владельца и заказа в порядке платёжного обработчика. Статус, причина, cancelled_by и очередь отмены PENDING-попыток сохраняются одной транзакцией. Внешние действия выполняет PaymentEffectsService после commit. Повтор сохраняет первый аудит. Позднее подтверждённое списание проходит PaymentCompletionService и фиксируется как compensation_required, без выдачи прав.

Возврат резервирует существующий RefundReservationService. RefundProcessingService отправляет accepted-операцию по cron и сверяет processing/unknown независимо от страницы. До подтверждения успеха заказ остаётся PAID и права сохраняются. Страница опрашивает состояние каждые пять секунд, пока оплата/возврат не завершены; принятый запрос не отображается как завершённый возврат. После окончательного отказа новая попытка возможна с сохранением журнала. Отсутствующий/неоднозначный подтверждённый платёж и legacy/административный источник требуют ручной проверки.

Миграция `1794900000000-admin-order-cancellation.ts` добавляет автора отмены с внешним ключом и индекс списка. Миграция проверяется в случайной одноразовой PostgreSQL-базе; основная база тестами не изменяется. Перед использованием обновлённого приложения примените миграции штатной командой `npm run am:bd:migrate`.

Основные проверки: API guards и входные данные — `admin-placed-orders.controller.spec.ts`; фильтры, аудит, гонки, откат outbox и интеграция возврата — `admin-placed-orders.postgres.spec.ts` с `ORDER_TEST_DATABASE_URL`. Frontend-тесты проверяют URL, доступ, реальный контрол причины, повторную отправку, ошибки и опрос до подтверждения результата.
