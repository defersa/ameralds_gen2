# Запросы и Signal Forms в Amstore

Применяй правила к изменяемому сценарию: при реализации создавай или исправляй запрошенный код; при ревью сообщай о найденных несоответствиях с местом, воспроизведением и последствиями. Не мигрируй соседние компоненты и не меняй бизнес-ограничения вне задачи.

## Сначала прочитай актуальные источники

Пути ниже относятся к корню Nx workspace Amstore. Соблюдай корневой и frontend `AGENTS.md`, особенно TypeScript conventions и правила авторизации.

- Образец компонента: `apps/am-front/src/app/features/main/admin/modules/settings/create-dialog/settings-create-dialog.component.ts` и соседний HTML.
- Обёртка запросов: `apps/am-front/src/app/utils/request-wrapper.ts`.
- Прикладной API-сервис соответствующей функции; для образца — `apps/am-front/src/app/services/app-settings.service.ts`.
- Контролы: `apps/am-front/src/app/cdk/signal-forms`.
- Общие сообщения: `apps/am-front/src/app/cdk/forms/errors/error-message-builder.ts`, `errors.pipe.ts` и шаблон `cdk/signal-forms/input-signal/input.component.html`.

Используй текущие реализации, а не сохранённые предположения об API. Если образец расходится с контрактом или требованиями задачи, не переноси расхождение в новый код. Для практического примера композиции прочитай [references/settings-create-dialog.md](references/settings-create-dialog.md).

## Новые запросы

- Создавай UI-запрос через `createRequestWrapper<typeof this.service.method>(this.service.method.bind(this.service))` в injection context: например, в инициализаторе поля компонента. `bind` сохраняет контекст сервиса.
- Вызывай существующий прикладной сервис и сгенерированный API-клиент. Не дублируй HTTP-вызов в компоненте, если сервис уже реализует этот контракт и проверки доступа.
- Используй `request.loading()`, `request.status()` и `request.errors()` как источник состояния запроса. Не заводи параллельные `loading`, `pending`, `failed` или `error` signals для того же состояния. Отдельные бизнес-состояния и черновик формы допустимы.
- Запускай `.request(args).subscribe(...)` из обработчика действия или управляемой загрузки. Не вызывай `.request()` из шаблона или `computed`. У текущей обёртки состояние становится `loading` при вызове `.request()`, поэтому не оставляй возвращённый Observable без подписки.
- В подписке обрабатывай успешный результат: обновление представления, навигацию или `dialogRef.close(result)`. Обёртка перехватывает ошибку и возвращает `EMPTY`; не рассчитывай на subscriber `error` как на основной обработчик ошибки.
- Обёртка уже использует `takeUntilDestroyed`. Не дублируй обработку ошибок и teardown без причины; учитывай, что отмена подписки не гарантирует отмену операции, уже принятой сервером.
- Блокируй повторную отправку и в обработчике, и в кнопке через `.loading()`. Для обработчика формы также проверяй `.invalid()`; пометь поля touched, чтобы причина отказа была видна.
- Сохраняй проверки доступа через существующие `AuthService.auth()` и `ProfileService.isAdmin()` в соответствующем сценарии/сервисе. Не считай DTO формы подтверждением роли или права доступа.

Ошибку запроса отображай через состояние обёртки. Не считай технический `HttpErrorResponse.message` готовым пользовательским сообщением: используй понятный fallback или существующее отображение кодов API. Для API с `expectedVersion`/409 обработай конфликт отдельно, предложи загрузить актуальную версию и сохрани черновик. Не повторяй изменяющий запрос автоматически с подменённой версией.

## Новая сигнальная форма

- Опиши модель формы отдельным типом или интерфейсом. Создай `signal<FormModel>(initialValue)` и `form(model, path => ...)`. Для новых Signal Forms не подменяй этот подход `FormGroup`, `FormControl` или ручной синхронизацией `valueChanges`.
- Сохраняй вывод типов для `inject`, `computed` и очевидных начальных значений; используй явные generics для `null`, пустых массивов и неоднозначных моделей. Nullable поле формы и обязательное поле DTO — разные контракты: явно проверь значение перед сборкой payload, не подавляй проблему `as` или `!`.
- Связывай существующие `amstore-*-signal` контролы через `[formField]="settingsForm.field"` и импортируй `FormField`. Не дублируй передачу `value`, `errors`, `touched` и прочего состояния, которое предоставляет эта привязка.
- Используй встроенные `required`, `min`, `max`, `email`, `pattern`, когда они выражают нужное ограничение. Проверку целого числа добавляй отдельно, только если этого требует контракт: `type="number"`, `min` и `max` сами по себе её не обеспечивают. Не копируй диапазон AppSettings в другие формы.
- Отдавай структурированные ошибки с общим `kind`. Общие тексты регистрируй в `ErrorTemplates`, а не в валидаторах каждой формы. Для нового `kind` добавляй соответствующий шаблон с нужными данными. Например, встроенный `min` передаёт `{ kind: 'min', min }`, `max` — `{ kind: 'max', max }`; это не старый формат `minValue: { current, expected }`.
- Используй существующий пайп `errors` внутри контрола. Не создавай рядом вторую систему сообщений и не вводи специфичный для компонента `kind`, если подходит общий `required`, `min`, `max` или `integer`.
- Для управления доступностью используй актуальную перегрузку: `disabled(path.field, { when: () => this.request.loading() })`. Не передавай функцию вторым аргументом напрямую — такая перегрузка deprecated в используемой версии Angular.

## Если форма находится в диалоге

Используй существующий `DialogService` и типизированные `MAT_DIALOG_DATA`/`MatDialogRef`. Успешный результат возвращай родителю для обновления списка. Проверь отмену, закрытие по Escape/backdrop и возможность отправить форму во время анимации закрытия: отключённой кнопки недостаточно для защиты обработчика. Согласуй блокировку закрытия с состоянием запроса и возвращай возможность закрыть окно после ошибки.

## Проверка результата

Выбери проверки, соответствующие изменению:

- Для формы проверь ввод через настоящий контрол и вывод сообщений через `errors`: пустое значение, границы диапазона, исправление ошибки; дроби, `0` и `false` — согласно контракту, не по предположению.
- Для запроса проверь повторный submit во время загрузки, успешный результат и ошибку с возможностью повторить действие. Для версионирования проверь 409 и сохранение черновика; для диалога — отмену и возвращаемый результат.
- Запусти затронутые тесты и ESLint исходников. Для изменённого Angular-кода проверь сборку; команды возьми из frontend `AGENTS.md`.
- Если задача ограничена изменением тестов, сохрани реализацию компонента и явно опиши закреплённое поведение. Не объявляй изменение ожиданий исправлением бизнес-логики.

В результате кратко укажи изменения или findings и выполненные проверки с ограничениями. Скилл задаёт процесс реализации и ревью; не добавляй обязательные зависимости, lint-правила или массовые правки только ради его применения.
